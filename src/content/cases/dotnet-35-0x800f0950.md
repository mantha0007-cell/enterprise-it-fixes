## Short answer

If .NET Framework 3.5 setup returns `0x800F0950`, first record the exact Windows release and how the feature was installed. Microsoft lists several .NET 3.5 servicing errors with documented meanings, but its published error tables do not define `0x800F0950`. Treat the code as a clue to investigate, not proof that WSUS, a missing source, or corrupted Windows files caused the failure.

## Our diagnostic lens

Use three facts to choose the next check: **Windows build → installation method supported by that build → first useful error in the servicing log**. This avoids applying advice for a different code or Windows release. A source-path fix is relevant only when the failed operation actually requested feature files from that source.

## What the sources establish

Microsoft's .NET Framework 3.5 installation article says other codes may appear beyond those covered in its table. That article documents 0x800F0906, 0x800F081F, 0x800F0907, and 0x800F0922; it does not assign a cause to 0x800F0950. Microsoft's deployment error table likewise explains specific codes rather than this one.

One Microsoft Q&A thread reports 0x800F0950 while installing .NET 3.5 on Windows 11 23H2. A staff response discusses update-source connectivity and management policy as possibilities in that reported environment. This is an individual troubleshooting exchange, not a Microsoft error-code specification, so use it to form checks rather than as a diagnosis.

## Check these details first

1. **Record the Windows version and build.** Open Start, run `winver`, and note the edition, version, and OS build. Do not publish tenant names, device names, or other internal identifiers when sharing logs.
2. **Record the installation path.** Note whether the failure came from Windows Features, DISM, PowerShell, an application installer, or a managed deployment tool. Include the exact time and any accompanying message.
3. **Check the supported method for that release.** On Windows 11 26H1 (build 28000) and later, Microsoft says .NET Framework 3.5 uses a release-specific standalone installer; it is no longer enabled as a Windows component. On other releases, follow the method Microsoft lists for that version.
4. **Inspect the servicing log around the failure time.** Review `%windir%\\Logs\\CBS\\CBS.log` and `%windir%\\Logs\\DISM\\dism.log` if DISM was involved. Look for the first failing operation and any more specific code nearby. Redact usernames, paths, tenant or company names, and machine identifiers before sharing excerpts.
5. **For a managed PC, ask the administrator to verify feature-source policy.** WSUS, Configuration Manager, or Windows Update policy can affect where optional-feature payloads are obtained. Do not change a domain-managed policy locally based only on `0x800F0950`.

## Choose the next step from the evidence

- If logs show a more specific documented code, follow the guidance for that code. For example, `0x800F081F` has its own source-missing guidance; see [our guide to 0x800F081F](/cases/windows-update-0x800f081f/).
- If the more specific code is `0x800F0906`, Microsoft documents a .NET 3.5 download failure; see [our guide to that condition](/cases/dotnet-35-0x800f0906-download-failure/).
- If the selected source is missing, unreadable, or for a different Windows release, have the administrator verify a supported source before retrying. A source issue should be supported by the operation or log, not inferred from `0x800F0950` alone.
- If the logs do not identify a source or payload failure, preserve the log excerpt and exact build/method for a targeted support investigation. Avoid broad permission resets, disabling update policy, or repeatedly running repair commands without a matching finding.
- If the device is on Windows 11 26H1 or later, use the standalone installer documented for that release instead of the older optional-feature workflow.

## What not to conclude

This code alone does not establish that Windows Update is blocked, that WSUS is misconfigured, that the local component store is corrupt, or that an ISO will fix the issue. Similar-looking .NET installation errors can have distinct documented meanings. Identify the failed operation and surrounding evidence before selecting a change.
